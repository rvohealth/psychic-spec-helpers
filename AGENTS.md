# AGENTS.md - AI Agent Instructions

## Public Error Exports

Export an error only when a developer of a Psychic application needs to throw
it or should reasonably be able to catch it as part of an expected,
well-functioning application workflow. An error being useful for debugging,
logging, or framework internals does not by itself justify a public export.
Compatibility-only residue (an error kept exported only for backward
compatibility, not because new code should throw or catch it) must be
documented as such, not treated as proof it still belongs in the public API.

## Starting New Work

Before creating a branch for new work, run `git fetch origin` and check whether
the current branch's work is already in `main`. It is when either:

- the branch has no commits ahead of `origin/main`
  (`git rev-list --count origin/main..HEAD` prints `0`), or
- its pull request is merged and `HEAD` is that pull request's head
  (`gh pr view --json state,headRefOid`).

Pull requests here are squash-merged, so `git branch --merged` cannot tell.

If the work is in `main` and the working tree is clean, branch from
`origin/main`. Otherwise, stop and ask the owner whether to build on
`origin/main` or continue from the current branch. Do not choose for them.

## Breaking Changes

Every Psychic application that depends on `@rvoh/psychic-spec-helpers` is a
caller, including apps generated by any past version of create-psychic and apps
nobody here has seen. Its helpers run in every such app's unit and feature spec
suites, and in psychic, psychic-websockets and psychic-workers. A change that
makes any existing caller's code stop compiling, or behave differently, is
breaking. That includes:

- removing or renaming an export, method or option;
- making an optional parameter or property required;
- removing or changing a default value (a default is part of the API);
- narrowing a type the package accepts, or widening a type it returns;
- changing the parameter types of an exported class's constructor;
- changing runtime behavior a caller can observe.

Rules:

- **Do not make a breaking change without the owner's explicit approval.** A
  bug note, an audit item or a reviewer's suggestion is not approval. When the
  recommended fix would break callers, stop and bring the owner the cost and a
  non-breaking alternative (documentation, a TSDoc warning, a new opt-in
  option).
- **A major version is not a remedy.** Bumping the major version does not make
  a break acceptable; every app that upgrades still has to fix its specs. Never
  offer a major release as the way to ship a breaking change.
- **Fixing an inconsistency at the edges is not the same as breaking the
  suite.** When two things that look the same to a caller behave differently
  (text hidden with `display: none` matched while text hidden with
  `visibility: hidden` did not; a declared type that contradicts what the
  runtime requires), making them consistent can break the few specs that relied
  on the odd half. With the owner's approval, that can ship in a minor version,
  provided ordinary usage of the helper is unaffected. The PR and the CHANGELOG
  must say exactly which caller code stops compiling or behaves differently, and
  why the change is worth it. A change that would fail the specs most apps
  already have is never in this category.
- **A trap is not a production bug.** If a behavior only misleads code nobody
  has written yet, and that code fails loudly on its first run, fix it with
  documentation, not by breaking the callers who use the behavior correctly.
- **Checking a few callers is not a consumer survey.** The current create-psychic
  scaffold and a handful of apps do not show what every app does. Older
  scaffolds and single-front-end apps rely on defaults that newer or
  multi-client apps override. Assume something relies on every default and every
  accepted type.
- **Prove a change is non-breaking before calling it that.** Build the
  declarations on `origin/main` and on your branch and diff them, then read
  every removed or changed line as a potential break:

  ```sh
  git worktree add --detach ../psychic-spec-helpers-main origin/main
  ln -s "$PWD/node_modules" ../psychic-spec-helpers-main/node_modules
  (cd ../psychic-spec-helpers-main && ./node_modules/.bin/tsc -p tsconfig.esm.build.json)
  rm -rf dist && ./node_modules/.bin/tsc -p tsconfig.esm.build.json
  diff -ru ../psychic-spec-helpers-main/dist/types dist/types
  git worktree remove --force ../psychic-spec-helpers-main
  ```

  The main worktree borrows this branch's `node_modules`; if the branch changes
  dependencies, run `pnpm install` there instead of linking.

- **Pin public defaults and signatures with specs**, such as a spec that relies
  on the default and `expectTypeOf(...)` checks, so removing one fails the suite
  instead of passing silently.

## CI Tooling: Industry Standards Only

Use the standard, documented mechanism a tool already provides, such as pnpm's
`minimumReleaseAge` for dependency cooldowns. Never hand-write CI scripts,
guards, or harnesses that re-verify a tool's own configuration. If a protection
needs enforcing against edits to its configuration, use code review, CODEOWNERS,
or branch protection on the configuration files, not a custom check. An agent
that believes a custom CI check is needed must stop and ask the owner, naming
the standard mechanism it could not find.
